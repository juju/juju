# Juju Documentation Rules

This file defines the core philosophy and structure for Juju documentation.

## Quick Reference for AI Agents

**Core principle:** Follow [Diataxis framework](https://diataxis.fr/) with strict modularity - content appears in ONE location only.

**Documentation placement:**
- **Reference** = What things are: entities, tools, mechanisms, and the contract of each call (who may make it, its rules, its errors). Not the steps a person follows
- **How-to** = The task flow through an entity's lifecycle (what you DO), including automatic operations. Not attribute lists or error catalogs
- **Explanation** = Why it matters, architectural context
- **Tutorial** = End-to-end learning paths

**Reference docs (docs/reference/):**
- Entity pages follow one section grammar (see "The Entity Reference Page Form"); other pages keep the entity or tool as the subject of every section title (e.g., "Database schema" not "How databases work")
- Order: broad -> specific, with implementation depth only on the page that owns the mechanism
- A fact has one owning page; every other page links
- Link to how-to guides for the steps

**How-to guides (docs/howto/):**
- Title pattern: "How to manage \<entity\>"
- Section pattern: "To \<accomplish task\>, \<do action\>"
- Order: lifecycle logic (create → view → inspect → modify → destroy)
- Keep entity in section headings (e.g., "View a database's schema" not "Viewing schemas")
- Include both manual AND automatic operations

**Cross-references:**
- "See also" = lateral reference to entity/concept docs (at top of how-to)
- "See more" = zoom-in to tool reference (after each command demonstration)
- Place tool references AFTER output/explanation, not immediately after command
- One reference link per new tool/command demonstrated

**Diagrams:**
- One model for the whole doc set: `docs/juju.ggarch` (ggarch), one view for each figure. A node, record, or edge is declared once; a page that needs a new entity extends the model and never starts a model of its own. Embed views with `{ggarch}`
- Never commit rendered SVGs; the docs build renders them. Colour means ownership only (see "Diagrams" below)

**Visual hierarchy:**
- `{warning}` = Critical constraints, safety information
- `{dropdown}` with `:color: success` = Tips, workflow advice
- `{dropdown}` with `:color: info` = Contextual information for specific audiences
- `{dropdown}` with `:color: warning` = About safety/write operations
- `{note}` = Important practical information (always visible)
- `{ibnote}` = Cross-reference links

**Code blocks:**
- Use `text` for commands and output
- Use `sql` for SQL queries and CREATE TABLE statements
- Always include empty line before opening backticks
- Include sample output after commands when helpful

**Naming conventions:**
- Entity page sections: `<Entity> database schema`, `<Entity> change streams`, `<Entity> calls`, `<Entities> and model migration` (never "data model")
- "Types of \<entity\>" only for mutually exclusive alternatives (e.g., `status.md`)
- Use realistic UUIDs and model names (not "default" - use "frontend", "backend")

**DO NOT:**
- Duplicate content across doc types (strict sorting: pick ONE location)
- Put a procedure in reference docs (the steps belong in how-to; the call's contract stays in reference)
- Put attribute lists in how-to docs (attributes belong in reference)
- Edit autogenerated docs manually (`.../list-of-juju-cli-commands/`, `.../list-of-hook-commands/`, controller config keys)
- Use metalanguage sections ("Prerequisites", "Tips") - integrate or use dropdowns
- Duplicate upstream documentation (SQL, YAML, etc.) - link to it

**Writing style:**
- Active voice: "To do X:" not "X can be done by:"
- Em-dash: ` -- ` (spaces around two hyphens) in prose
- Colon inside the bold term in bullet lists: `**Term:** Definition.`
- No version scoping of any kind (see "Version Information")
- Consistent entity names (controller model database, not "controller database")

## Charter: what `docs/` documents

`docs/` is the top-most `doc.go`. It documents what the codebase exports -- everything projected onto a user interface (CLI, API wire, status, log lines, database tooling) -- and the cross-cutting mechanisms that no lower-level document can own, at mechanism level, in surfaced vocabulary. Everything else is implementation and lives in the code.

The Locality Principle in `AGENTS.doc-dot-go-rules.md` is the parent rule: document everything at the smallest scope where it can be accurately documented, and send cross-package concerns to project-wide documentation, which is `docs/`. The writing guidelines of that file therefore apply here too: contracts, not implementation; verify every claim against the code and remove what it does not support; when in doubt, omit.

A package's `doc.go` gets two gates from the Go toolchain: godoc renders only exported identifiers (the visibility rule), and its readers are package users (the reader definition). Prose has no compiler, so `docs/` states both gates itself ("What Goes On a Reference Page") and adds the rule that locality implies and never says: one owning page for each fact.

## Documentation Framework

The Juju documentation follows the [Diataxis framework](https://diataxis.fr/) with specific implementations for each documentation type:

**Reference** (in `docs/reference/`) -- Defines what things are in Juju:
- **Concept references**: High-level concepts (e.g., high-availability, scaling)
- **Entity references**: Concrete entities users work with (e.g., controller, model, database, application)
- **Tool references**: Commands and interfaces (e.g., juju CLI, juju_db_repl, juju-dashboard)
- **Process references**: Operations and procedures (e.g., upgrading, migrating, backing up)

**Juju-specific implementation for Reference:**
- **Attributes, mechanisms, and call contracts, not procedures**: Reference docs describe what entities *are* and what each call does (who may make it, what it checks, what it returns and refuses). The steps a person follows to reach a goal belong in how-to guides
- **Maintain the central subject**: All section titles keep the entity or tool as the subject (e.g., "Database schema", "Controller configuration", not "How databases work")
- **Broad to specific ordering**: Progress from high-level structure to technical detail. Implementation depth appears only on the page that owns the mechanism
- **Cross-reference to how-to**: Link to operational guides for practical usage

**How-to guides** (in `docs/howto/`) -- Shows how to accomplish specific tasks:
- Structured around entity lifecycles
- Each section represents a moment in the lifecycle
- Sections ordered by lifecycle logic: creation → viewing → inspection → modification → removal
- Within lifecycle stages, order from common to specific operations

**Juju-specific implementation for How-to:**
- **Entity-centric titles**: "How to manage \<entity\>" (e.g., "How to manage databases", "How to manage controllers")
- **Task-oriented sections**: Each section follows "To \<accomplish task\>, \<do action\>" pattern
- **Maintain entity focus**: Section headings keep the entity as the red thread (e.g., "View a database's schema", "Query a database", not "Viewing schemas", "Querying")
- **Operations included**: Document both manual and automatic operations as the task flow -- what the user does, and what happens automatically along the way. The mechanism itself (a state machine, who drives it) belongs to its own reference page, which the how-to links
- **Tool references**: Link to tool reference docs after demonstrating each command
- **Entity references**: Link to entity reference docs at the top for context

**Explanation** (in `docs/explanation/`) -- Provides understanding and context:
- Architectural decisions and design rationale
- Why things work the way they do
- Broader context for features and patterns

**Tutorials** (in `docs/tutorial/`) -- End-to-end learning paths:
- Guide beginners through complete workflows
- Currently minimal in Juju documentation

This framework ensures documentation serves different user needs: understanding (explanation), reference (lookup), guidance (how-to), and learning (tutorial).

## Documentation Process for New Features

When documenting a new feature, follow this process:

1. **Identify the entity** -- What is the new thing users will work with? (e.g., database, secret, offer)

2. **Identify the tools** -- What commands or interfaces let users interact with this entity?

3. **Create entity reference** (in `docs/reference/`) -- Define:
   - What the entity is
   - Entity attributes, structure, and characteristics
   - Its records, change streams, and calls, in the section grammar of "The Entity Reference Page Form"
   - Only what a reader can meet on a supported surface (see "What Goes On a Reference Page")

4. **Create tool reference** (in `docs/reference/`) -- Document:
   - Complete command syntax
   - All options and flags
   - Technical details
   - Examples

5. **Create how-to guide(s)** (in `docs/howto/`) -- Show:
   - How to work with the entity through its lifecycle
   - Use "See also" links for the entity reference (lateral reference)
   - Use "See more" links for tool references after each command demonstration (zoom-in)

This ensures users get the full picture: **what** it is (entity reference), **how** to use it (how-to), and **detailed command reference** (tool docs).

## Autogenerated Documentation

**DO NOT manually edit autogenerated reference documentation.** These files are regenerated from source code during the documentation build process. Any manual changes will be overwritten.

Two kinds of contributor edit the docs: **prose-only** contributors (edit hand-written Markdown, only need `make html`) and **source + autogeneration** contributors (change Go source that some pages are generated from, and must regenerate and commit the output). See `CONTRIBUTING.md` for the two paths.

**Currently autogenerated documentation:**
- **Juju CLI command reference** -- All individual command pages in `docs/reference/juju-cli/list-of-juju-cli-commands/`
- **Hook command reference** -- All individual command pages in `docs/reference/hook-command/list-of-hook-commands/`
- **Controller configuration keys** -- `docs/reference/configuration/list-of-controller-configuration-keys.md`
- **Model configuration keys** -- `docs/reference/configuration/list-of-model-configuration-keys.md`

**To update autogenerated documentation:**
- For CLI commands: Update command definitions in the source code and command help text
- For hook commands: Update hook command definitions in `scripts/md-gen/hook-commands/`
- For controller configs: Update controller configuration schema in source code
- For model configs: Update the model configuration schema in source code
- Regenerate: Run `make regenerate-docs` from the `docs/` directory, then commit the changed pages

**See:** `docs/scripts/autogenerate-docs.py` for the complete autogeneration implementation.

### CI and verification

The generated pages are committed, and the docs CI enforces two distinct outcomes:
- `make verify-docs` (from `docs/`) regenerates and fails if any autogenerated page differs from what is committed. Run it locally before pushing.
- The docs CI (`docs.yml`) runs on every PR that triggers it (any generator-input or `docs/` change). It has two jobs: `autogenerated-docs`, which runs the freshness check and is **merge-blocking** (if the source changed and the generated pages were not updated, the PR cannot merge); and `html`, which runs the full Sphinx + Playwright/excalidraw build and is **informational** (other doc-build issues do not block the merge). The docs workflow runs per-PR only; it is not a merge-queue gate.
- The docs CI trigger is the set of generator inputs (`cmd/`, `controller/`, `environs/config/`, `internal/configschema/`, `internal/worker/uniter/runner/jujuc/`, `scripts/md-gen/`, `docs/`), so backend-only `.go` changes do not run it.

## Diagrams

Diagrams are drawn from one plain-text model, `docs/juju.ggarch`, with [ggarch](https://github.com/tmihoc/ggarch). The model describes Juju once; each figure is a view of it.

- **One model.** Declare every node, record, and edge once, in the one model in `docs/juju.ggarch`. Everything that describes the system lives in the model; a view only selects, positions, and annotates. A `diagram` or `sequence` view selects what one figure needs, so renaming a node updates every figure. A page that needs a new entity extends the model, never starts a model of its own, and never re-declares another page's record. Node ids are unique in the one model: when an architecture entity and a database record share a table's name, the entity's id takes the `arch_` prefix (`arch_model`) and the record keeps the bare table name (`model`). Keep to the existing node and edge types.
- **Embed a view** in a page with the `{ggarch}` directive. `:file:` is relative to the page, `:view:` is the view name, `:caption:` carries the technical detail of the layer the figure shows, defining each term in brackets where it first appears, and `:alt:` describes the picture for readers who cannot see it. Start a caption with its subject and its point, as the example below does, so it reads like every other caption in the docs. The text around the figure stays light and leaves the detail to the caption:

  ````text
  ```{ggarch}
  :file: ../juju.ggarch
  :view: The insight
  :caption: Each unit runs a unit agent, a charm, and the workload.
  :alt: Three units, each with a unit agent, a charm, and a workload.
  ```
  ````

- **Slideshows.** Use `:slides:` with view names separated by `|`, and `:slide-captions:` with one caption per slide, to show several views one at a time. Keep each sequence to the simplest scenario, without alternatives or loops.
- **Visual grammar.** Colour has one meaning, ownership. An orange border marks Juju machinery and a grey border marks anything outside Juju. Nodes have no fill and are all rounded rectangles. A corner badge says what kind of node it is, and `deployed: true` adds a cloud badge to an entity that runs on a node from a cloud. A dotted orange border (`type: entity`) marks a logical entity that the controller keeps, such as a model or an application, and a dashed border means a lifecycle stage. Edge dashes and arrowheads say how two nodes interact. Add a node type only when it needs a new badge or a new border.
- **Preview.** Run `make run` in `docs/`. Edits to a page or to `docs/juju.ggarch` rebuild the affected pages. To validate the model without a full build, run `ggarch check docs/juju.ggarch` from the docs virtualenv (`docs/.venv/bin/ggarch`).
- **Rendered SVGs stay out of the repository.** The docs build renders them, and reviewers see them in the Read the Docs preview of the PR.
- **Renderer version.** `docs/requirements.txt` pins ggarch to a full commit SHA. Bump the SHA in the same PR when a diagram needs a newer renderer, and check that the docs build still passes.
- **Details.** ggarch's [SKILL.md](https://github.com/tmihoc/ggarch/blob/main/SKILL.md) is the authoring guide: file anatomy, node and edge types, positions, sequences, and troubleshooting.

## How-to Guides

### Entity-Centric Structure

How-to guides are organized around **entities** (controllers, models, databases, applications, etc.). Each guide answers: "What can I do with this entity?"

**Title pattern:** "How to manage \<entity\>" (e.g., How to manage controllers, How to manage models, How to manage databases)

### Entity Lifecycle Ordering

Sections within a how-to should follow the entity's **lifecycle logic**:

1. **Access/Create** -- How to get or create the entity
2. **List/View** -- How to see what exists
3. **Inspect** -- How to view details or configuration
4. **Modify** -- How to change the entity
5. **Query/Use** -- How to work with the entity
6. **Remove/Destroy** -- How to delete the entity

Not all entities have all stages. Order sections logically based on typical workflows.

**Example (Manage databases):**
- Access databases
- View the database cluster
- List databases
- Switch to a database
- View a database's schema
- Query a database
- Query across databases
- Modify a database
- View a database's change history

### Section Structure

Each section should follow the pattern: **"To \<accomplish task\>, \<do action\>"**

**Good:**
- "To switch to a model database by its name:"
- "To see what columns and data types a table contains:"

**Avoid:**
- Generic headings like "Prerequisites" or "Tips"
- Command-centric organization ("Run .tables")

### Context Establishment

Balance context establishment to support both first-time readers and returning users who jump to specific sections.

**Pattern:**
- **Establish once:** An early section (e.g., "Access the databases") establishes the working environment
- **Self-contained sections:** Each section should be understandable on its own for users who return directly to it
- **Clarify transitions:** Add brief context when the interaction model changes or when a command's syntax differs significantly

**Example:**
- "Access the databases" establishes you're working in the REPL
- Sections showing dot commands (`.models`, `.switch`, `.tables`) are self-contained because the dot prefix signals REPL context
- "Query a database" adds clarifying context ("type SQL statements directly at the REPL prompt") because raw SQL lacks visual cues and users may return to this section repeatedly

**Rationale:** Users often return to how-to guides to reference specific tasks. Sections should be independently usable without requiring full re-reading, while avoiding verbose repetition in every section.

### Child Entities and Bridge Sections

Guides can include subsections for **child entities** when they're tightly coupled to the parent.

**Example:** In "How to manage actions", include:
- Manage action tasks
- Manage action operations

**Bridge sections** can connect to related entities:
- In "How to manage clouds", include "Manage cloud credentials" that links to the full "How to manage credentials" guide

## Lateral References

Link to **concept docs** at the top of how-to guides using `{ibnote}`:

```markdown
```{ibnote}
See more: {ref}`entity-concept`, [External docs](https://...)
```
```

> **Note:** Consider placing a brief intro sentence before lateral reference links for better AI processing. Starting documents with links may cause AI systems to prioritize link-following over content understanding. This pattern is under review.

Link to **tool references** at the end of relevant sections using "See more" `{ibnote}` (zoom-in principle):

```markdown
```{ibnote}
See more: {ref}`command-reference`
```
```

**When to include tool reference links:** Include a reference link after demonstrating each new tool or command. This provides readers immediate access to complete technical details.

**Placement within sections:** Tool reference links should appear after showing command output and providing explanation, not immediately after the command itself. This allows readers to see what a command does before diving into detailed reference documentation.

**Good:**
```markdown
To list all tables:

\`\`\`text
.tables
\`\`\`

Sample output:

\`\`\`text
table_name
application
unit
\`\`\`

\`\`\`{ibnote}
See more: {ref}`juju-db-repl-tables`
\`\`\`
```

**Avoid:**
```markdown
To list all tables:

\`\`\`text
.tables
\`\`\`

\`\`\`{ibnote}
See more: {ref}`juju-db-repl-tables`
\`\`\`

Sample output shows...
```

## Content Hierarchy: At-Issue vs Not-At-Issue

Use **dropdowns** for supplementary content readers can choose to view. Label clearly:

- **`Tip:`** -- Workflow advice, best practices
- **`Background:`** -- Conceptual information that provides context
- **`Troubleshooting:`** -- Problem-solving help
- **`About...` with `:color: warning`** -- Critical safety information

**Naming guidance:** Use "Background:" for conceptual information, not "Reminder:" (which implies the reader has seen it before).

**Placement:** Immediately before where most relevant (after intro paragraph, before the command).

**Example:**
```markdown
```{dropdown} Background: What's a view?
A view is a virtual table defined by a SQL query.
```
```

## Writing Style

- Use **entity names** consistently (controller model database, not "controller database")
- Use **em-dash** as ` -- ` (two hyphens with spaces) in prose paragraphs
- Use **colon inside the bold term** in bullet lists where a term is followed by its definition or description, and end with a period:
  - Good: `**Authentication required:** Only authenticated agents can access the database.`
  - Avoid: `**Authentication required** -- Only authenticated agents can access the database`
- Use **active voice**: "To do X:" not "X can be done by:"
- Provide **context**: "In a model database, to view applications:"
- Use `text` for code blocks (not `bash` or `sh`)
  - **Exception:** Use `sql` for SQL queries and CREATE TABLE statements to enable syntax highlighting
- Keep code blocks clean: empty line before and after triple backticks
- Include sample output after commands when helpful
- Use realistic UUIDs and names in examples

## Upstream Documentation

**Point to upstream; don't duplicate.**

When Juju documentation references technologies maintained by external projects (SQL, YAML, cloud APIs, etc.):

- **DO** link to upstream documentation as the source of truth
- **DO** provide brief guidance on how to use that technology with Juju (e.g., "To modify data, use standard SQL write operations")
- **DON'T** duplicate upstream syntax references, tutorials, or specifications

**Good:**
```markdown
To modify data, use standard SQL write operations.

```{ibnote}
See more: [SQL documentation](https://www.sqlite.org/lang.html)
```
```

**Avoid:**
```markdown
To modify data, use standard SQL write operations:

INSERT INTO table_name (column1, column2) VALUES (value1, value2);
UPDATE table_name SET column1 = value1 WHERE condition;
DELETE FROM table_name WHERE condition;
```

**Rationale:** This keeps our documentation coherent while avoiding maintenance burden and version drift. We maintain Juju-specific guidance; upstream maintains their specifications.

## Version Information

Do not scope any fact to a version: no "in 4.1", no `versionadded`, `versionchanged`, or `deprecated` directives, no "new in" or "since" notes. Version facts go stale. The release notes and the per-version documentation carry them. The one exception is the how-to for the 3.6 to 4.1 upgrade, whose subject is the version transition.

## What to Avoid

- Metalanguage sections ("Prerequisites", "Tips") -- integrate or use dropdowns
- Command-first organization -- organize by entity, not command
- Generic troubleshooting sections -- place contextually as dropdowns

## Concept Documentation

Concept docs (in `docs/explanation/`) explain **what** an entity is, **why** it matters, and **how** it fits into Juju's architecture.

**Pattern:** A concept doc should link **down** to related tool references and how-to guides using lateral references at the end or in relevant sections.

**Example:** A database concept doc should link to:
- {ref}`juju_db_repl` (tool reference)
- {ref}`manage-the-databases` (how-to guide)

This provides readers with a complete path: concept → reference details → practical usage.

> **Future enhancement:** Consider using sphinx tags to enforce and validate these cross-reference patterns automatically.

## Reference Documentation

Reference docs (in `docs/reference/`) define **what things are** in Juju -- entities, tools, processes, and concepts. Think of an IKEA manual: when you open the package, you first get an inventory that defines each part. That's your reference documentation.

**What belongs in reference:**
- Entity definitions (controller, model, database, application, unit, etc.)
- Tool specifications (juju CLI, juju_db_repl, juju-dashboard, etc.)
- Process references (scaling, upgrading, removing things, etc.)
- Technical specifications and APIs

**Key principle:** If you're defining what something **is**, that's reference. If you're explaining why it **matters** or how it **fits** into architecture, that's explanation/concept.

**Example:** The database entity reference defines what a database is in Juju, its types (controller database, model databases), and technical characteristics. The explanation would cover broader architectural implications and design decisions.

### What Goes On a Reference Page

**Key principle:** A fact earns a place only if all three hold:

1. **It is true.** Checked against the code as it is now, and re-checked whenever the page is touched. Truth is a standing duty, not a one-time gate.
2. **A reader can meet it.** It appears where a reader looks: a command's output, an API call's reply, a status, a log line, or the database through the supported tools (`juju dump-db`, `juju-db-repl`, backups).
3. **Someone is asking, and this page owns the answer.** Reference readers: people running Juju; people building tools that talk to its API; people writing charms; people debugging a controller with direct database access. AI assistants read too, but they change how we write -- every term linked or defined, one home per fact -- never what goes in. Not Juju developers; the code is their documentation.

**When the tests disagree:**

- **Meetable, but this page's reader is not asking:** move the fact to the page whose reader is, or cut it.
- **Someone asks, but they cannot meet it:** write only what they can meet.
- **Neither:** it stays in the code.

**Ownership:** every fact has exactly one owning page; every other page links. Big machinery -- how a model moves between controllers, how watchers work -- also has one owning page, and it is not exempt: it must itself answer a reader's question, told as what happens, who drives it, in what order, and where each step surfaces, in names a reader can trace to a command, an API, or a log line.

This governs `docs/reference/`. How-to guides may keep a labeled corner for Juju developers (for example, the Dqlite core-dump guide) -- labeled, so no one mistakes it for operator guidance.

### The Entity Reference Page Form

The audiences behind the third test, and the questions each asks:

| Audience | Their questions |
|---|---|
| Operator (reads status and logs) | What is X? What can I do to X, and who may? Which states can X be in, and which follow which? Why did this fail, and what do I do? What happens to X during migrate, upgrade, destroy? Where do I see X, and what does its log line mean? |
| Client or tool developer (human or AI writing against the API) | Which calls read or change X, with what request, result, and errors? What access does a call need? What invariants must my tooling respect? Which watcher follows X, and what does each delivery carry? Which exact strings and codes can the wire return? |
| Charm developer (the client is the unit agent) | Which hooks fire for my charm, and why? What may my charm read or change, with what rules and errors? Which statuses can it set or receive? Am I the leader? What happens to its world during maintenance? Bounded to Juju's behavior toward the charm, not the craft of writing one |
| Storage or incident inspector (database access) | Which records make up X's storage, in which database? What must always hold of them, so that a dump can be judged sane? What bookkeeping does the storage layer keep? |
| AI reader | The union of the above. It changes how pages are written, never what goes in |

The test filters; it does not decide a page's form. The reader's question decides the owner of a fact, not the subject and not where the fact lives in the code. Mentioning is not restating: a page may name a fact with a link (a record that another page owns appears as a linked context chip) and may not re-describe it. A mechanism with its own reference page (model migration, watchers, the database) keeps its machine there, and the call that starts it links it.

**Section grammar.** Each section appears only when its facts exist, in this order:

| Section | Holds |
|---|---|
| Lede (no heading) | One definition sentence (the kind of thing, then what sets it apart), then at most two sentences on where it lives, who holds it, how it comes and goes |
| `<Entity> database schema` | Figure first, then the records with their rules. Only what the database enforces or the schema fixes, and only what an interface shows |
| `<Entity> change streams` | Only if a client, agent, or worker can follow the entity: the changes that the holders follow, delivered through a watcher |
| `<Entity> calls` | An opener defining the set, then one `###` for each call |
| `<Entities> and model migration` | Only the exception to the generic export, in one paragraph |

Never: an Identity section, an errors section, a section that announces itself. A mechanism page (model migration, watchers) leads with its machine (the phase or state diagram), then what happens in each state, then who drives it, then its records and streams. The page set comes from the manifest; a page's level (page or section) is derived from the code (own typed ID, own facade method, own lifecycle) and recorded in the commit.

**The top of a page** is a `See also:` `ibnote` linking the Juju how-to and the Terraform Provider for Juju page.

**A call** is a `###` under a `## ... calls` section and nowhere else. It is titled with a gerund and the entity (`Adding SSH keys`) and opens with the gerund phrase as the subject, saying what the call does. Then:

- `Caller:` who may make it. For a client, the user it acts for, with the linked access level ("A client, for a user with write access to the model") and the block that must not be on. For an agent, its identity ("A unit agent, for its own unit."). Levels attach to users, never to clients.
- `Rules:` every rule of the call, nested under one bullet.
- `Errors:` the message the client sees, its code, a trigger, and a remediation. A remediation says what to do, never a consequence.

**Database schema rules.**

- A rule stays only if the database enforces it (unique index, not-null or check constraint, trigger, foreign key) or the schema fixes the allowed values. Find the constraint in the consolidated release DDL (`domain/schema/*/4.0.15-*-release.ddl`), never in a per-table patch alone. A rule that a service, facade, or worker applies when a call runs goes in that call.
- A record, field, or sentence stays only if a reader can meet it through a surface the page documents. Otherwise: hide it (internal bookkeeping), contain it (a record that explains a shown one rides as a linked context chip), or relocate it (prose for another page's reader moves there).
- No table names, column lists, or `.ddl` pointers in entity-page prose. The mapping lives with the database tooling and on the database page, whose subject is the storage layer.
- A status with allowed transitions has its values in the schema. Its state diagram and transition table live in the call that changes it, or on the mechanism page when the mechanism has one.
- A kind that records decide (peer relation, cross-model relation) is described in the bullet of the record that decides it. The base case comes first.

**Text rules.**

- Every opening sentence is a definition. "X is how Y does Z" is not one.
- A bullet list is built up to: the paragraph before it ends in a colon and says what the list holds. A list of one item is prose. No counting intros.
- Say what is true, never what is absent.
- One subject for each sentence. Do not glue facts with ", and": name the real relation (so, then, because, when). "And" stays for same-kind items and for two verbs of one subject.
- Oxford comma. American spelling.
- "Operation" is the domain word for one run of a script across units (`juju operations`). One documented API interaction is a "call".
- Hook commands, never "hook tools". Every specific hook or hook command links to its documenting section; a name with no page stays in plain code font.
- Never "databag": say settings.
- Link jargon at its first mention in each section, or define it in a parenthetical. Never link a CLI command page and never write "the CLI offers": reference pages are client agnostic.
- Define "unit agent" once, in the calls introduction: the process that runs the unit's charm, logged in as its unit, acting only for that unit.
- A file's name matches its page title.

**Figures.** On reference pages only, never on how-tos. The first thing in its section. The caption carries the takeaway (what to read first, the rule the edges imply); the alt text carries the inventory, in plain English. A schema figure shows records only and a sequence figure shows software only. A sequence figure appears only when a call crosses at least three actors, at least one outside the controller, and the order decides what the reader sees.

**Mechanical checks** before a page is shown: the page-rules checker (titles, forbidden phrases, spelling, list intros, ", and" glue), the error-contract check in `docs/scripts/check_error_contract.py` (every documented error message is raisable by the source), `ggarch check`, and both builders (`dirhtml` and `latex`) into fresh directories.

### Section Ordering

Reference docs should progress from **broad to specific**:

1. Brief intro defining what the entity is
2. High-level structure or organization (e.g., the database schema)
3. Technical implementation details (e.g., what technology it uses) -- only on the page that owns the mechanism

This allows readers to understand the big picture before diving into specifics.

**Example (Database reference):** the lede, `Database schema`, `Database change streams`, `Database calls`, and `Databases and model migration`, in that order.

**Cross-references:** Place "See also" links to related how-to guides upfront, before or immediately after the intro, so readers can quickly navigate to operational docs if needed.

## Tool Reference Documentation

Tool reference docs (in `docs/reference/`) provide complete technical details about commands, options, and usage.

### File Naming

Name reference files after the **tool name users invoke**, not the underlying technology:

- **Good:** `juju-cli.md`, `juju-dashboard.md`, `juju-db-repl.md`
- **Avoid:** `client.md`, `dqlite-repl.md`

Exception: Entity references use the entity name directly (e.g., `model.md`, `controller.md`).

### Anchor Naming

**General rule:** All anchors use lowercase with dashes as separators (no underscores).

**For document and entity references:**

```markdown
(database)=
# Database

(juju-cli)=
# Juju CLI
```

**For section anchors within documents:**

Use the full section title in lowercase with dashes replacing spaces:

```markdown
(database-access-and-security)=
## Database access and security
```

**For command references:**

Commands use dashes, even if the actual command name contains other characters:

```markdown
(juju_db_repl)=
# `juju_db_repl`
```

Command-specific anchors should follow the pattern `<tool>-<command>`:

```markdown
(juju_db_repl-models)=
### `.models`
```

### Section Organization

Organize tool references by **tool capabilities or attributes**, not by metalanguage categories:

**Good (by capability):**
- Overview
- Database architecture
- Basic commands
- Navigation
- Schema introspection
- Query execution
- Cluster management

**Avoid (metalanguage):**
- Commands
- General commands
- Database navigation commands

This pattern applies to CLI tools, REPLs, and other interactive tools.

### Entity Reference Section Naming

Entity pages use the section grammar in "The Entity Reference Page Form". `Types of <entity>` is for classifying mutually exclusive alternatives, where a thing is one kind or another (`Types of status`). Tool and process pages name sections by what they hold, never by metalanguage.

### Command Documentation

For commands that are alternatives (not aliases), list them together in the heading:

```markdown
### `.exit`, `.quit`
```

Use **Usage:** for syntax specifications, not **Aliases:** unless one is truly an alias of another.

## Cross-Documentation Patterns

When documenting a feature that spans multiple documentation types (concept, reference, how-to):

1. **Concept doc** links down to tool reference and how-to guide
2. **How-to guide** links up to concept doc (top) and over to tool reference (per section)
3. **Tool reference** links to how-to guide for practical usage

This creates a documentation triangle where users can move between understanding (concept), reference (details), and practice (how-to).

> **Future enhancement:** Consider sphinx tags or other tooling to validate these cross-reference patterns and ensure documentation completeness.

### Avoid Duplication Across Documentation Types

**Principle:** Content should appear in **one primary location** based on Diataxis type. Use cross-references rather than duplicating content.

**Strict sorting rule:** Even when content could reasonably fit multiple documentation styles (e.g., a concept could be explained in reference *or* how-to), choose the **single most useful location** and use cross-references ("See also", "See more") to connect related content. Don't hedge by putting variants in multiple places.

**Why this matters:**
- Reduces maintenance burden (update once vs. updating multiple locations)
- Prevents inconsistencies and version drift
- Forces clearer thinking about what content belongs where
- Makes documentation easier to navigate
- Eliminates user confusion about which version is authoritative

**How to choose where content belongs:**
- **Explanation/Concept:** What something is, why it matters, architectural context
- **Reference:** Complete technical definitions, specifications, entity characteristics (attributes, properties, structure)
- **How-to:** Practical step-by-step workflows, entity lifecycle operations, operational procedures (including automatic operations)
- **Tutorial:** End-to-end learning paths for beginners (we have few of these)

**Key distinction for operations:** If content tells the user what to do, it belongs in how-to guides. If it states a mechanism (a state machine, who drives it, what a call checks and refuses), it belongs on the reference page that owns the mechanism or the call, and the how-to links to it.

**When in doubt:** If content serves multiple purposes, choose the **most specific** location and link to it from other docs. Prioritize the style that serves the most common use case.

**Examples:**
- Database security measures belong in the security explanation doc, not duplicated in the database reference
- Tool command details belong in tool reference, not duplicated in concept docs (concept docs can mention tools exist and link to them)
- When-to-use guidance can appear in concept docs with link to how-to; brief version can appear in how-to intro
- Emergency recovery procedures belong in operational how-to guides, not scattered across multiple reference docs

**Trade-off:** Occasionally, this means some content appears in only one Diataxis type even though it might seem relevant to multiple. That's acceptable -- use cross-references to guide readers where they need to go.
